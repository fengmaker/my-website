# 笔记写作准则

适用范围：本站 JSSP 专题、`Heuristic/fjsp_learning` 的学习资料及后续 FJSP 调度学习笔记。新增、修改和 review 笔记时均使用本准则；用户反馈优先，新的约定合并进相应条目。

## 1. 数学对象统一使用数学记号

正文、表格、自检题、答案和图中的数学对象保持同一套符号。第一次出现时解释含义，之后使用已经定义的记号。

| 对象 | 统一记号 | 含义 |
|---|---|---|
| Job | $J_j$ | 第 $j$ 个作业/工件 |
| 工序 | $O_{j,k}$ | $J_j$ 的第 $k$ 道工序 |
| 机器 | $M_r$ | 第 $r$ 台机器 |
| 工序指定机器 | $\mu_{j,k}$ | 工序 $O_{j,k}$ 指定的机器；FJSP 的机器选择另行定义 |
| 加工时间 | $p_{j,k}$ | 工序 $O_{j,k}$ 的加工时长 |
| 开始时间 | $s_{j,k}$ | 工序 $O_{j,k}$ 的开始时刻 |
| 结束时间 | $c_{j,k}$ | 工序 $O_{j,k}$ 的结束时刻 |
| Job 完工时间 | $C_j$ | $J_j$ 最后一道工序的结束时刻 |
| 最大完工时间 | $C_{\max}$ | 所有 job 完工时间的最大值 |

具体工序写成 $O_{1,2}$，避免在数学叙述中用普通文本 `O12` 代替。工件、机器和最大完工时间也相应写成 $J_1$、$M_2$、$C_{\max}$。两个工序索引用逗号分开，便于区分 $O_{1,12}$ 与 $O_{11,2}$。

代码中的真实变量名、文件名和数据格式可以保留原样，并使用代码格式；解释其数学含义时，明确它与数学记号的对应关系。

## 2. 公式、路线与表格的写法

行内公式使用 `$...$`，独立公式使用单独成行的 `$$` 包围，块前后留空行。源码示例如下：

```markdown
工序 $O_{1,2}$ 使用机器 $M_2$。

$$
c_{j,k}=s_{j,k}+p_{j,k}.
$$
```

工艺路线、机器顺序和约束推导用数学公式或带数学记号的表格展示。用于讲解的路线不放在普通代码块中，否则 `$...$` 只会显示为源码。代码块留给真正的程序、命令、输入数据、伪代码或 Markdown 写法示例。

每个公式附近说明符号含义、成立原因和适用条件。长公式按推导步骤拆开，避免横向溢出；表格中的公式尽量简短。表格里的绝对值等需要竖线时，使用 `\lvert`、`\rvert`，避免与列分隔符冲突。

## 3. 加粗与 Markdown 渲染

加粗使用配对的 `**`，标记内侧紧贴内容。在正文中，加粗片段与相邻的连续文字之间留一个普通空格；句末标点通常放在加粗外。强调短语或结论，避免整段都加粗。

稳定写法：

```markdown
这叫 **不可抢占**（non-preemptive）。
但 **更好不等于已证明最优**。
```

需要特别注意的反例：

```markdown
但**“更好”**。
```

本次已用 CommonMark 兼容解析器复现：上面的反例会保留星号；在开头标记前加空格后可以生成加粗。Markdown 强调标记的识别受相邻空白与标点影响。这是本项目选择稳定写法的原因，并不表示所有行内加粗都必须加空格才能解析。[CommonMark 强调规则](https://spec.commonmark.org/0.31.2/#emphasis-and-strong-emphasis)

数学符号保持在数学环境中；需要强调某个数学结论时，加粗其文字解释。标题、列表、表格、块引用和公式前后安排空行，代码围栏与公式分隔符完整配对。

## 4. 图与正文保持一致

图中的工序、job、机器和目标值也使用下标。SVG 使用原生下标文本，例如 `tspan` 的基线偏移；支持数学排版的绘图工具使用相应数学环境。图片里的 `$O_{1,2}$` 源码不会因插入 Markdown 就自动变成公式。

图中工序索引、颜色、机器、时长和起止时间与正文逐项一致。颜色可以辅助识别，文字标签仍需完整；缩小图后也要能读清楚。图注说明它展示的是可行性、算法过程还是最优性证明。

## 5. 教材式讲解与逐节 review

先提出具体问题，用例子建立直觉，再引入符号和推导。区分定义、可证明性质、经验观察和算法选择；第一次出现术语时解释中文含义。

重要结论写明前提。例如固定机器顺序后，计算的是最早可行排程；说明关键路径与 makespan 的关系时，也明确所使用的排程条件。

尽量沿用贯穿实例，给出可手算的中间步骤，并配易错点、自检题和速记卡。涉及历史贡献、标准实例或公开参考值时，核对原始论文或官方来源。

每次提交一节供用户 review。修改后仍标为待 review，直到用户明确认可；再进入下一节。格式修订不自动代表内容已获确认。

## 6. 提交前检查

- [ ] 正文、表格、题目和答案中的工序等对象均使用统一数学记号。
- [ ] 下标索引、符号含义、公式环境和括号一致、配对完整。
- [ ] 讲解用的数学路线没有被普通代码块包住。
- [ ] 加粗片段可解析，渲染正文没有意外露出的 `**`；代码示例中的源码除外。
- [ ] 图与正文的数据、记号一致，下标能辨认。
- [ ] 例子的可行性、时长、完工时间和目标值核算正确。
- [ ] 相对链接和图片存在，review 状态准确。
- [ ] 在可用的 Markdown 预览中检查公式、表格、加粗和图片；说明未覆盖的渲染环境，避免把源码检查称作完整视觉验收。
