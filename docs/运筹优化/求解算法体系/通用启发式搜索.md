# 通用启发式搜索：表示、邻域与接受准则

启发式实现可以从五个问题展开：怎样表示解、怎样构造初解、怎样生成候选解、怎样接受候选解、何时停止。把这些职责分开，才能判断一次改进来自算子、评价方式还是计算预算。本文提供方法教程与教学片段；尚未开展性能实验。

## 先定义解和可行性

对称 TSP 可以用城市排列表示闭合回路，首尾的连接隐含在目标函数中。VRP 则需要多条路线，还要明确仓库、客户归属及车辆限制。相同的数组操作在两种问题上可能有不同含义。

| 职责 | 接口应回答的问题 |
| --- | --- |
| 表示与复制 | 解包含哪些决策？生成候选解是否会意外修改当前解？ |
| 可行性检查 | 是否恰好访问每个客户？容量、时间窗、先后访问等是否满足？ |
| 目标评价 | 距离、车辆数、违约代价的单位和优先级是什么？ |
| 构造与修复 | 插入失败时怎样处理？是否允许返回“无可行修复”？ |
| 搜索控制 | 算子怎样抽样？接受准则使用哪些状态？预算何时检查？ |

如果允许不可行中间解，应把真实目标与罚函数分开记录；改变罚系数后，不能直接比较新旧罚目标。最优可行解始终用同一个目标定义评价。车辆数优先、距离次优时，可以直接比较 `(车辆数, 距离)`，也可以在证明权重足够后使用加权目标。

## 当前解与历史最好解

当前解决定下一次从哪里搜索；历史最好可行解决定最后返回什么。模拟退火等方法可以接受变差的当前解，历史最好可行解不应因此丢失。

```text
current ← 构造初解并检查可行性
best_feasible ← current（仅当可行）
while 未达到停止条件:
    candidate ← 用选定算子生成独立的候选解
    评价 candidate 的可行性与目标
    if candidate 可行且优于 best_feasible:
        best_feasible ← 保存 candidate 的副本
    if 接受准则(current, candidate, 搜索状态):
        current ← candidate
    更新温度、禁忌表或算子统计等状态
return best_feasible（若不存在，明确报告未找到可行解）
```

只接受严格改进得到下降式局部搜索。允许受控的劣化、记忆或重启，可以探索其他区域，但不能据此宣称求得全局最优。停止条件应明确采用时间、评价次数、迭代次数还是无改进次数；这些预算不能混为一谈。

## 对称 TSP 的 2-opt 增量

设两条不相邻的边为 $(a,b)$ 与 $(c,e)$。删除它们，反转 $b$ 到 $c$ 的子路径，再连接 $(a,c)$ 与 $(b,e)$。当距离对称、目标只有各条边费用之和时：

$$
\Delta = d(a,c)+d(b,e)-d(a,b)-d(c,e).
$$

反转的内部边费用不变，因此只需评价四条边。这里的 $\Delta$ 是“新目标减旧目标”，负值表示改进。

```python
def two_opt_delta(tour, i, j, distance):
    # 前提：tour 是无重复城市的闭合回路排列，distance 是对称距离矩阵。
    n = len(tour)
    if n < 4 or not (0 <= i < j < n):
        raise ValueError("invalid cut positions")
    if j == i + 1 or (i == 0 and j == n - 1):
        raise ValueError("cut edges must not be adjacent")
    a, b = tour[i], tour[(i + 1) % n]
    c, e = tour[j], tour[(j + 1) % n]
    return distance[a][c] + distance[b][e] - distance[a][b] - distance[c][e]


def apply_two_opt(tour, i, j):
    # 切点须先经过上面的检查；返回新列表，避免污染 current / best。
    return tour[:i + 1] + tour[i + 1:j + 1][::-1] + tour[j + 1:]
```

非对称 TSP 中，内部弧反向后费用也会改变，上述四边公式不能直接使用。VRP 中，即使距离对称，还必须检查容量、时间窗及跨路线操作的约束。开发增量评价时，应在小规模输入上与完整重算核对；这项正确性检查不能替代求解性能实验。

## 从局部搜索到 LNS / ALNS

局部搜索通常改变少数相邻决策。LNS 先移除一部分决策，再通过修复重新组合，例如移除若干客户后按插入代价回填。移除规模影响搜索范围，修复失败也必须成为明确的返回状态。

ALNS 在此基础上维护多个破坏与修复算子，根据历史表现调整选择权重。实现时应写清奖励的触发条件、统计周期和权重更新方式；“找到新最好解”“改善当前解”“被接受”是不同事件。原始方法与问题背景见 [Ropke 与 Pisinger 的 ALNS 技术报告](https://backend.orbit.dtu.dk/ws/portalfiles/portal/3154899/An%20adaptive%20large%20neighborhood%20search%20heuristic%20for%20the%20pickup%20and%20delivery%20problem%20with%20time%20windows_TechRep_ropke_pisinger.pdf)。

每个搜索组件至少记录输入、输出、失败条件和随机源。算子需要共享状态时，明确哪些状态影响候选解、哪些只用于统计。这样可以单独替换算子，而不把评价逻辑复制到每个方法中。
